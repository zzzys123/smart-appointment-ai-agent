# Smart Appointment AI Agent - 系统评估报告

> 评估时间：2026-06-05  
> 评估模型：Qwen-Plus (通义千问)  
> 评估环境：本地 SQLite + FAISS 向量索引

---

## 一、评估目的

AI Agent 系统不同于传统软件，它的核心能力——意图理解、知识检索、多轮对话——都具有不确定性。仅靠"跑通了"不足以说明系统质量，需要用量化指标来回答三个关键问题：

1. **系统能不能听懂用户？** → 意图分类准确率
2. **系统能不能找到正确的知识？** → RAG 检索召回率
3. **系统能不能完成核心业务？** → 预约流程完成率

---

## 三、维度一：意图分类准确率

### 3.1 评估什么

TaskClassifier 是整个系统的"第一道关"。用户说的每一句话，都要先被分类为以下类别之一：

- `appointment`（预约任务）
- `query`（咨询/查询任务）
- `pay`（支付任务）
- `statistics`（统计任务）
- `other`（无关任务）

分类错了，后续所有处理都是错的。所以这个环节的准确率直接决定了用户体验。

### 3.2 如何评估

**方法**：构建覆盖各种表达方式的测试用例集，逐条喂给 TaskClassifier，对比预测结果和人工标注的期望结果。

**测试用例设计原则**：
- 每个类别覆盖多种自然语言表达（口语化、正式、简短、冗长）
- 包含容易混淆的边界用例（如"按摩"单独一个词，可能是咨询也可能是预约）
- 包含无关话题（天气、股票、闲聊）来测试拒绝能力

**用例分布**：

| 类别 | 用例数量 | 示例 |
|------|---------|------|
| appointment | 10 | "帮我预约今天下午3点的按摩"、"给我预约一个力气大的男技师" |
| query | 10 | "全身按摩多少钱？"、"你们有会员卡吗？" |
| pay | 2 | "预约已确认，用户选择了张伟技师做全身推拿" |
| statistics | 2 | "工作人员通知：8号技师已完成当前任务" |
| other | 8 | "今天天气怎么样？"、"帮我写一首诗" |

**执行方式**：
```bash
python -m evaluation.eval_classification
```

### 3.3 评估结果

```
总体准确率: 31/32 = 96.9%

各类别准确率:
  appointment     10/10    100.0%
  query           10/10    100.0%
  pay              2/2     100.0%
  statistics       2/2     100.0%
  other            7/8      87.5%
```

**唯一的错误**：
- 输入："你是谁？你能做什么？"
- 期望：`other` → 实际预测：`query`

### 3.4 结果分析

**优势**：
- 预约和咨询两个高频类别达到 100% 准确率，说明 Prompt 对核心场景的覆盖很好
- pay 和 statistics 虽然用例少，但都能正确识别，说明对特殊格式消息的处理没问题

**不足与改进方向**：
- "你是谁？你能做什么？" 被归类为 query 而非 other，原因是 LLM 认为这是在咨询系统自身的服务能力。这个边界可以通过在 Prompt 中补充"关于 AI 本身的问题不属于业务咨询"来优化
- other 类别的用例还可以扩充更多边界场景（如中英混杂、emoji、超长文本）
- pay/statistics 类别各只有 2 条用例，评估置信度不够高，建议后续补充到 5-8 条

## 四、维度二：RAG 检索召回率

### 4.1 评估什么

当用户问咨询类问题时，系统需要从知识库中检索到相关文档，作为 LLM 回答的依据。如果检索不到正确文档，LLM 要么凭空编造，要么给出"无法回答"——两种情况都影响用户体验。

**核心指标**：Top-3 召回率 — 在返回的前3条文档中，是否包含了能回答用户问题的内容。

### 4.2 如何评估

**方法**：构建标准问答对，每个问题标注"期望命中的关键内容片段"，然后检查实际检索结果中是否包含这些片段。

**评估流程**：
1. 对每个测试查询，调用 `KnowledgeService.search(query, top_k=3)` 获取检索结果
2. 将 Top-3 文档的 content + keywords 合并成文本
3. 检查期望的关键片段是否出现在合并文本中
4. 只要命中任意一个片段即认为该查询召回成功

**测试用例示例**：

| 用户查询 | 期望命中片段 |
|---------|-------------|
| "你们几点开门？" | 营业时间、上午9点、晚上10点 |
| "全身按摩多少钱？" | 全身推拿、120元、60分钟 |
| "办会员卡有什么优惠？" | 会员、充值、优惠、500元送50元 |

**执行方式**：
```bash
python -m evaluation.eval_rag_retrieval
```

### 4.3 评估结果

```
Top-3 召回率: 12/12 = 100.0%
平均片段命中率: 100.0%
```

所有12条查询全部在 Top-3 结果中命中了期望的文档内容。

### 4.4 结果分析

**优势**：
- 100% 的召回率说明当前知识库规模下（10条文档），FAISS + text-embedding-v3 的向量检索效果非常好
- 即使用户的表达和知识库原文不完全一致（如"几点开门" vs "营业时间"），语义检索仍然能正确匹配

**不足与改进方向**：
- 当前知识库只有 10 条文档，召回难度低。当文档数增长到 100+ 时，召回率很可能下降，需要持续监控
- 缺少"否定用例"——即故意问知识库中不存在的内容（如"你们做不做针灸？"），看系统是否会错误检索无关文档
- 评估指标可以更精细：除了"是否命中"，还可以看检索排名（正确文档是否排在第1位而非第3位）
- 建议后续引入 MRR (Mean Reciprocal Rank) 指标来衡量排序质量

## 五、维度三：预约流程完成率

### 5.1 评估什么

预约是系统的核心业务闭环。一个预约需要收集：时间、服务项目、时长、技师偏好（性别或指定技师）。评估重点是：

1. **一轮完成**：用户一句话包含所有信息时，能否直接完成预约
2. **缺失追问**：信息不全时，能否正确识别缺什么并追问
3. **多轮收集**：分多轮补全信息后，能否最终完成预约
4. **异常处理**：技师不空闲时的推荐流程、无关请求的转交

### 5.2 如何评估

**方法**：构建多种预约场景，模拟用户输入，观察 AppointmentAgent 的行为是否符合期望。

**测试场景设计**：

| 场景 | 输入 | 期望行为 |
|------|------|---------|
| 一句话完整预约 | "帮我预约今天下午3点的全身按摩，1小时，要男技师" | 直接预约成功 |
| 指定技师（可能不空闲） | "预约张伟技师，明天下午2点，做60分钟肩颈按摩" | 成功或触发推荐流程 |
| 缺少项目 | "帮我预约今天下午3点，1小时，男技师" | 追问服务项目 |
| 缺少时长 | "今天下午3点帮我约个全身按摩，要女技师" | 追问服务时长 |
| 缺少性别 | "帮我预约今天下午3点的按摩，1小时" | 追问技师性别 |
| 多轮补全 | "我想预约按摩" → "今天下午4点" → "1小时" → "要男技师" | 最终预约成功 |
| 无关请求 | "帮我写一首关于春天的诗" | 识别为无关或追问 |

**弹性期望说明**：
- 某些场景的结果取决于运行时状态（如技师是否空闲），所以设置了 `success_or_ask` 弹性期望
- LLM 可能推断默认值（如没说日期默认今天），这属于合理行为，不应算错

**执行方式**：
```bash
python -m evaluation.eval_appointment_flow
```

### 5.3 评估结果

```
流程判断准确率: 8/8 = 100.0%

各场景类型准确率:
  success         2/2     100.0%
  success_or_ask  2/2     100.0%
  ask_more_info   3/3     100.0%
  reject_or_ask   1/1     100.0%
```

### 5.4 结果分析

**优势**：
- 多轮对话能力验证通过：4轮逐步补全信息最终成功完成预约
- 缺失字段识别准确：缺项目、缺时长、缺性别三种情况都能正确追问
- 天气集成工作正常：预约成功后能调用天气 API 生成个性化提醒

**不足与改进方向**：
- 预约场景的用例数量偏少（8个），建议扩充到 20+ 以提高覆盖度
- 缺少"取消预约"、"修改预约"等场景的测试
- 缺少并发场景测试（多用户同时预约同一技师）
- 没有测试"技师推荐确认"完整流程（用户说"好"或"不"之后的处理）
- 多轮补全的轮数没有上限控制评估（如果用户一直不给完整信息，系统是否会无限追问）

## 六、综合评价

### 6.1 系统整体表现

| 评估维度 | 得分 | 评级 | 判定标准 |
|---------|------|------|---------|
| 意图分类 | 96.9% | ✅ 优秀 | ≥90% 优秀，80-90% 良好，<80% 需优化 |
| RAG 检索 | 100.0% | ✅ 优秀 | ≥85% 优秀，70-85% 良好，<70% 需优化 |
| 预约流程 | 100.0% | ✅ 优秀 | ≥80% 优秀，60-80% 良好，<60% 需优化 |

### 6.2 核心优势

1. **意图分类 Prompt 设计质量高**：通过举例说明和角色设定，LLM 能准确区分预约、咨询、支付等不同意图，几乎没有跨类别误判
2. **向量检索语义理解能力强**：用户的自然语言表达和知识库原文存在表述差异时，embedding 模型仍能正确匹配
3. **多轮对话状态管理可靠**：预约字段逐步收集的机制工作正常，不会丢失已收集的信息
4. **业务闭环完整**：从意图识别到信息提取到技师匹配到数据库写入到天气提醒，全链路通畅
5. **5 个分类全覆盖**：所有分类类别（appointment、query、pay、statistics、other）都有完整的处理逻辑，不存在"搭架子"问题

### 6.3 已知局限

1. **评估规模有限**：总计 52 条测试用例，无法覆盖所有边缘情况。生产环境应持续收集真实用户对话来扩充评估集
2. **知识库规模小**：当前仅 10 条文档，100% 召回率在文档量增长后必然下降
3. **缺乏对抗性测试**：没有测试注入攻击（如"忽略之前的指令"）、超长输入、特殊字符等鲁棒性场景
4. **评估不含延迟指标**：每轮对话的响应时间没有纳入评估，实际用户体验受延迟影响大
5. **LLM 输出不确定性**：同一输入多次运行可能得到不同结果（虽然 temperature=0 减轻了这个问题）

### 6.4 后续优化计划

| 优先级 | 改进项 | 预期收益 |
|--------|--------|---------|
| P0 | 扩充测试用例至 100+ 条 | 提高评估置信度 |
| P0 | 加入否定用例和对抗测试 | 发现系统脆弱点 |
| P1 | 引入 MRR 指标评估检索排序 | 更精细衡量 RAG 质量 |
| P1 | 加入响应延迟统计 | 量化用户体验 |
| P2 | 定期回归评估（CI 集成） | 防止代码变更导致退化 |
| P2 | 收集真实用户 bad case | 持续改进系统 |

```
evaluation/
```

