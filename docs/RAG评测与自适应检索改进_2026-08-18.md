## 四、第四至第六阶段：质量、路由与可观测性

### 1. 端到端质量评测

新增 `evaluation/eval_end_to_end_quality.py`，覆盖：

- 真实 Hybrid 检索；
- 无答案证据门；
- 生产咨询 Prompt；
- 回答生成与结构化引用；
- LLM Judge 的正确性、忠实度、相关性和安全边界评分；
- 逐题检查点、单题超时、基础设施错误隔离及断点续跑。

评测器新增 `--case-id`，开发阶段可以只运行受影响案例，不需要每次完整调用 60 条。

### 2. 动态重排与路由

实现 `off / always / adaptive` 三种模式，并保留旧 `RERANK_ENABLED` 兼容路径。
当前候选方案为：

- 普通查询：保持 Hybrid；
- 高置信 Hybrid：直接返回，不使用随机性更高的重排；
- 复杂预约、会员、安全和规则边界：允许选择性 LLM 重排；
- Cross-Encoder：保留显式启用能力，默认不自动路由；
- 精排超时或异常：回退 Hybrid；
- 只有确定可能发生重排的查询才扩大候选池，避免改变普通 RRF 基线。

### 3. 检索可观测性

每次检索生成唯一 `trace_id`，记录：

- Dense、BM25、RRF、Rerank 的文档顺序和耗时；
- 动态路由原因、置信度和触发信号；
- 原始分、重排分、融合分；
- 证据门接受或拒绝的文档及具体原因；
- 无答案、错误和重排回退状态。

默认只记录 query 的 SHA-256；只有显式开启后才持久化原始问题，避免手机号等隐私
内容无意落盘。

## 六、针对五个失败案例实施的改进

最初 Qwen3.7-Plus 的五个失败案例为：

- `chunk_booking_cross_section`
- `semantic_full_body_avoid_area`
- `exact_technician_010`
- `rerank_member_priority_boundary`
- `chunk_booking_success_boundary`

实施的通用改进包括：

1. 生成器与 Judge 使用相同的证据格式，包含 `source_id`、来源、章节标题、分块和正文。
2. Prompt 要求业务规则、金额、时间和项目名称尽量沿用证据原文，不擅自具体化。
3. Qwen Judge 的安全结果改为 0-1 分数并按 0.8 判定，兼容模型返回 `0.5` 等数值，
   避免布尔 Schema 解析失败。
4. LLM 重排关闭 Qwen 思考模式，降低延迟和结构化输出波动。
5. LLM 重排采用 0-10 分，只有达到 8 分的候选才能作为证据门的补充通道。
6. BM25 索引加入来源编号和章节标题。
7. 增加少量可审计的业务同义词扩展，例如“空位→空闲”“占住→占用/完成预约”、
   “脚→足部”“已订时段→已确认排班”。该方案仍属于候选优化，不能继续根据每个
   失败样本无限追加词条。

最新代码下的 6 条定向集（原五条加 `chunk_store_last_start`）结果为 **6/6 通过**，
无基础设施错误，平均端到端评测延迟约 11.12 秒，P95 约 14.70 秒。

## 七、回归过程中发现的问题与纠偏

完整 60 条 adaptive 评测曾多次在中途停止，没有形成正式新基线。停止原因包括：

- Cross-Encoder 修复边界案例时破坏普通语义案例；
- 对所有 adaptive 查询扩大候选池会改变 RRF 排名，即使最终没有重排；
- LLM 重排存在随机误排，同一案例定向通过后，在完整运行中可能把无关文档打成 10 分；
- 修改 Judge 上下文和 Schema 后，评测口径已经变化，不能继续和旧结果直接比较。

由此确定：**不再要求 60/60，也不再采用“失败一条、修改一次、完整跑一次”的方式。**

后续验收原则：

- `infrastructure_error_count` 必须为 0；
- 安全、隐私、医疗边界和无答案拒答不能退化；
- 总体质量相对基线非劣，而不是必须全部通过；
- 修改期间只跑受影响用例；
- 候选版本稳定后完整 60 条只跑一次；
- 后续把开发集和未参与调试的 Holdout Set 分开，防止对现有样本过拟合。

Golden v2 不要求 60/60。它用于判断版本是否稳定、关键能力是否退化，以及成本和
延迟是否可接受。
